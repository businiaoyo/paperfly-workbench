## 问题与实现

test.3 只保存首成员占比，其余成员均分，主界面也只显示第一条分隔手柄；拖动时只画导线，释放后才改变窗口。用户明确要求所有相邻应用都可调节，并且拖动过程中窗口比例立即变化。

- `SplitDivider` 改为每对相邻应用一个 Handle。三应用显示两条，合并成四应用即有三条；横向和纵向共用几何规则。每条只占自身的小触摸区域，均有无障碍描述与步进操作。
- `PaneLayout.moveDivider` 在相邻两成员原有总额内重新分配，不移动其他分隔，不改变其他成员份额。保留最小可操作尺寸，已有更小成员不因首次抓取而跳大。
- MOVE 用 `StageActivity.splitPreview` 的临时卡片立即变换现有 TextureView；画面持续更新，两侧窗口即时跟随。取消、多指、旋转、失去前台或卡片变化恢复原几何，未提交比例不写入草稿。
- 松手沿 `CardSession` 和原存储队列提交，异步调整实际尺寸变化的应用画布，复用显示器和有效 Surface，不盖“正在调整窗口”。其他成员画布不调整。
- 面板展示每个成员的占比，提供自动/左右/上下排列及“均分所有应用”。点按任一分隔条仍可打开面板。
- 默认新卡片等分。合并两组按成员数分配总面积，保留两组内部已有相对比例。普通模式继续沿 test.3 的 Dock 画布基准铺满；全屏、侧栏和交换继续共用整组映射。

实时预览是对真实持续画面的缩放，允许暂时的非等比伸缩；应用内部内容重排在松手后的逻辑画布 resize 完成。没有每个 MOVE 都触发第三方应用 configuration change，也没有用截图代替画面。静止后继续按实际画布适配，最小画布、像素取整及厂商专用画布仍可能留必要边距。

## 数据边界与迁移

纯 Java `SplitWeights` 管成员份额，`WorkspaceCard.paneWeights` 按稳定窗口 ID 保存，不依赖成员序号、名称或 displayId。成员重排、焦点变化和自由布局修改保留对应份额；增删时按剩余总额归一化。

`WorkspaceCodec` 的 schema 8 写入 `paneWeights`，不再写旧 `firstWeight`；schema 1–7 按旧首成员值及其余均分迁移，保留原画面比例、稳定身份、焦点、归属及已保存组合。模型保留派生的旧访问器，仅兼容旧调用。缺项、未知项、非正/非有限值或总和非法的配置拒绝读取并保留原文件；未来版本保护和写入失败重试沿用 Repository。没有扩大服务权限或加入同步磁盘 I/O。
