# 原生工作台研究与重做依据

研究日期：2026-11-07。本文保留重做前的研究与设计判断。同日后续已实现 0.5.0 的可信虚拟显示器路线，实测结果见 [重做验证记录](rebuild-validation.md)；下文“待验证”描述的是研究阶段，不能替代后续测试结论。

## 结论与任务边界

用户需要的是：当前应用保持为主任务，其他应用在侧边待命，点选后平滑交换主次；应用状态连续，快速操作能得到响应。约束为免 root、同一个 APK、自带服务、电脑 USB 激活后可以拔线使用，设备重启后重新激活。

0.4.0 的静态侧卡、厂商普通小窗恢复和串行切任务不能满足这个目标。重做应以持续存在的应用画面为基础，统一调度显示变换、主次位置与输入焦点。不能用全局关闭系统动画或忽略连续点击来代替正确的切换。

证据分为三类：下文标记“实测”的内容来自连接的 vivo 平板；苹果部分来自官方文档和 WWDC 文字稿；新架构及其性能目标在研究时属于设计决策，当时尚未证明能在荣耀上实现。没有取得苹果或 vivo 私有窗口管理器源码。

## vivo 实测对象与方法

- 系统报告机型 iPA2693，Android 17 / API 37，固件 DPD2653_A_17.0.6.19.W10；不据此推断零售型号或系统营销名称。
- 横屏实际画面 2304×1440，密度 400。
- 通过原生界面操作设置、计算器、时钟；读取任务、窗口、显示层及界面状态，保存切换前后的截图。
- 系统三项动画倍率全程保持 1.0。没有安装 APK、修改框架、注册 TaskOrganizer 或变更开发者设置。
- 原始本地证据位于 `.runtime/vivo-research/`，不纳入版本控制。精简结构数据见 [native-stage-observations.json](native-stage-observations.json)。完整窗口转储含无关后台应用，未复制到公开研究资料。

## 原生操作规则

| 操作 | 实测结果 | 对本项目的约束 |
| --- | --- | --- |
| 当前 App 内从右下角斜向内滑动 | 当前 App 成为主窗，侧边出现工作台；首次出现引导 | 进入动作围绕当前任务；不用先完成一套应用选择流程 |
| 点侧边加号并选应用 | 主窗不变，新应用加入侧位 | 添加和切换是两个操作 |
| 点一个侧窗 | 该应用到主位，原主应用进入被点中的侧位，其他侧位保持 | 明确维护槽位，不按“应用列表减去当前项”重排全部卡片 |
| 秒表运行后退到侧边 | 两次截图分别显示 00:02.18、00:06.85 | 侧位支持真实持续更新，不能默认用离开时截图替代 |
| 约 147 ms 间隔连续选择设置、时钟 | 最终主窗为时钟，最后一次选择生效 | 新意图不能被“正在切换”直接丢弃 |
| 主窗顶部菜单“切换全屏” | 时钟全屏，设置和计算器恢复为普通全屏后台任务，专用根任务变空 | 退出时恢复任务，不能留下收纳气泡或隐藏窗口 |

引导还明确提示侧窗左滑可移除。本轮未单独执行移除手势，因此不把它计为完成的实机测试。

连续点击的 146.6 ms 是主机发出 ADB 命令的时间差，不是触摸硬件时间或响应延迟。只证明本次最后目标被执行，不能据此断言 vivo 内部采用动画重定向还是合并队列。截图采样也不足以测得精确帧率、动画时长或曲线。

## 主次交换时，哪些东西保持不变

这台 vivo 上存在系统专用的 `vivo-multi-task` 窗口模式。根任务 80 由 organizer 创建，设置任务 93、计算器任务 98、时钟任务 99 都作为子任务放在显示器 0 上。

| 项目 | 计算器在侧位 | 计算器在主位 |
| --- | --- | --- |
| Task ID / 进程 PID | 98 / 10603 | 98 / 10603 |
| Activity | `com.android.bbkcalculator/.Calculator` | 同一 Activity 记录 |
| 应用逻辑边界 | 2304×1440 | 2304×1440 |
| 系统主次标记 | `isMainAppInVivoMultiTask=false` | `true` |
| 显示缩放 | 0.1388889 | 0.71875 |
| 显示位置 | 左侧槽位 | (504, 120) |

时钟交换也保持任务 99、进程 595 及应用逻辑边界。三应用时，侧位 1、2 的位置分别为 (145,231)、(145,515)；主位显示矩形为 (504,120) 到 (2160,1155)。这些是此设备此布局的观测值，不应硬编码为跨设备布局。

任务转储包含 `positionIdInVivoMultiTask`、`pointInVivoMultiTask`、`scaleInVivoMultiTask` 和 `mPointInfoInVivoMultiTask`。侧窗四角形成带透视的四边形。SurfaceFlinger 层级包含 `TaskLeash-93/98/99`、实际 Task 层及 `VivoMultiTaskUiManager` 等管理层。捕获到的切换中间画面中，主窗和侧窗同时改变位置与大小。

据这些证据可判断：本次交换主要改变应用画面的呈现位置、缩放和主次角色，应用没有为这次主次交换反复缩成小尺寸布局再放大。无法仅凭这些转储还原完整的厂商合成代码、事务时序与曲线。

侧位生命周期不能一概而论：计算器、时钟在样本中可保持 RESUMED，设置曾为 STOPPED，之后又出现 RESUMED。秒表实测证明至少该应用侧窗在更新，不证明所有应用或受保护画面都始终实时。

## 苹果资料中应学习的规则

苹果将当前窗口置于中央，其他窗口退出当前工作区域；可以将多个窗口组成一组，整组进入或离开。辅助面板、弹出层和模态窗口应跟随当前工作，不能像另一个主窗口一样把它挤走。对我们的意义是：主任务可以是一个窗口组，输入法、弹窗及应用内辅助窗口必须跟随正确任务，而非独立侧卡。[Apple：What's new in AppKit，WWDC22](https://developer.apple.com/videos/play/wwdc2022/10074/)

本项目首版重做仍聚焦一个主应用与侧应用交换；分组是后续扩展，不能以它增加首个可用版本的复杂度。vivo 官方也将主次协同与多应用并行区分为不同布局场景；本项目按用户要求优先主次协同。[vivo：OriginOS](https://www.vivo.com.cn/originos)

## 0.4.0 为什么仍然不好用

| 当前实现 | 可定位的代码 | 直接影响 |
| --- | --- | --- |
| 主窗是系统 freeform，侧卡是快照，两者分开管理 | `StageEngine.switchTo()` / `StageActivity.renderCards()` | 侧卡与真实窗口没有共同的持续画面及交换过程 |
| 热切换仍重排任务并调用 `startActivityFromRecents` | `StageEngine` 的 show 事务和恢复调用 | 与厂商的收纳、恢复、标题栏动画发生耦合 |
| 每次切换读取/修改全局动画倍率、抓快照、轮询和等待 | `TransitionScale` / `StageEngine` | 关键路径延迟高；屏蔽动画没有建立正确的画面连续性 |
| `if (switching) return`，完成后再锁定 350 ms | `StageActivity.select()` 与卡片点击监听 | 用户最后一次选择丢失 |
| 移除所有卡片再按原应用顺序重建 | `StageActivity.renderCards()` | 其他应用跟着换槽位，破坏位置记忆 |
| 厂商机型专用 0.76 缩放补偿 | `StageActivity.select()` | 依赖特定固件的普通小窗行为，无法构成通用工作台 |

历史记录的热切换服务耗时 1308–1363 ms，之后界面还锁定 350 ms；首次整理样本为 1980 ms。即使任务最终可见，这种交互仍不合格。25 项单元测试、构建通过和稀疏截图只能说明相应代码检查通过，不能证明视觉连续、输入响应或整体可用性。

## 重做的结构与状态规则

保留 USB 激活、内置服务与调用方身份验证，替换任务呈现和切换模块。三个职责需要分清：

1. **任务承载**：维护真实任务及持续画面，负责生命周期、输入焦点、键盘、弹窗和退出恢复。返回“首帧可用”事件，而不是让界面用固定等待时间猜测。
2. **工作台状态**：记录主任务 ID、每个侧位的任务 ID、最新选择、过渡代号；任务身份与显示位置分离。
3. **画面合成**：根据当前画面状态，同一时序推进交换双方的位置、大小、圆角和层级。主次交换期间不改变应用逻辑分辨率，不在每帧重新启动或调整应用任务。

例如 `主=A，侧1=B，侧2=C`，点击 C 后目标为 `主=C，侧1=B，侧2=A`；B 的位置不变。过程中再点 B，要记住新的意图，从当前画面继续或合并后转向 B；旧回调不能把主位又写回 C。任何一次新选择都不能被忙碌标记静默丢弃。

没有可用画面时保留当前可操作主窗，显示目标正在加载，收到真实首帧后再交换。已开始的触摸序列不能因主位变化而把后续 MOVE/UP 发到另一个应用；切换时应完成或取消原输入序列，再更换焦点。

图片快照只允许作为明确标识的异常降级，不能作为默认侧位。动画关键路径中移除全局 settings 改动、外部命令、同步截图和固定 sleep。

## 跨品牌后端：需要先验证的两条路线

| 路线 | 要验证的能力 | 不能预先假定的部分 |
| --- | --- | --- |
| 系统任务容器与远程 Surface 动画 | 在不抢占厂商现有管理器的前提下，获得目标任务的合法显示层控制与同步事务 | shell 有权限不代表能长期持有任务 leash；不能全局注册 organizer 后假定不会接管用户任务 |
| App 承载的可信虚拟显示器，直接输出到本 App 的 Surface | 两个真实 App 持续渲染；主位触摸、多点、输入法、弹窗、焦点正常；退出可恢复 | 不是复制截图或编码视频；多显示器兼容、应用限制、资源消耗和任务迁移需逐项实测 |

AOSP 公开说明了窗口动画与界面帧同步、对应用 Surface 施加变换的实现思路；这是设计依据，不能当作 vivo 源码或本 App 已能使用的证明。[AOSP：Synchronized app transitions](https://source.android.com/docs/core/display/synched-app-transitions)

scrcpy 官方已经展示 ADB 驱动的新虚拟显示器、应用启动和显示器内输入法策略。这里只借鉴可行性与系统接口，不要求用户安装 scrcpy，也不把其显示到电脑的方案等同于本机工作台。[scrcpy：Virtual display](https://github.com/Genymobile/scrcpy/blob/master/doc/virtual-display.md)

本轮只读检查发现，两台设备的 shell 均获授 `MANAGE_ACTIVITY_TASKS`、`CONTROL_REMOTE_APP_TRANSITION_ANIMATIONS`、`ADD_TRUSTED_DISPLAY`、`INJECT_EVENTS` 等相关权限。这是继续做后端实验的依据，不是跨品牌能力验证完成。不能直接移植 vivo APK 或套用它的私有窗口模式常量。

## 首个必须通过的实机验证

优先在已授权的荣耀设备上验证两个真实 App 的最小场景；第三个 App 用来检验连续选择。以下均为待验证标准，不是本轮已通过结果。

- 计算器保留输入内容；运行中的秒表退到侧位继续刷新，再回主位时无重启、白屏或内容重排。
- 主窗与选中侧窗同时交换，第三个槽位不移动；连续交换 30 次后状态正确。
- 在过渡中以 100–150 ms 间隔选择新目标，最后目标总能生效；用带时间戳的完整帧记录核查跳帧、闪黑与位移，不能只检查最终截图。
- 目标画面就绪时，触摸反馈在下一至两个显示帧出现；交换和输入响应延迟分别统计，不把命令返回时间当成动画时长。
- 验证文字输入、键盘遮挡与切换、返回键、应用内弹窗、多点触摸、旋转与 Home 后恢复。
- 验证退出、App 强停及服务中断，任务能恢复、虚拟显示器及 Surface 能释放；全局动画倍率不变。
- 完成 USB 激活后拔线测试；所有设备命令显式指定序列号，避免两台设备同时连接时误操作。

只有承载、输入和连续交换通过后，才做侧窗透视、弹簧曲线、分组等外观与扩展；不能再把“真实 App 最终显示出来”作为交付标准。

## 本轮结束状态

测试秒表已暂停并复位为 0，回到闹钟页，既有闹钟保持关闭。通过原生菜单退出工作台并返回桌面；系统 `vivo_multi_task_mode=0`，三项动画倍率仍为 1.0。未更新荣耀上的 0.4.0，也未向 vivo 安装本项目 APK。
