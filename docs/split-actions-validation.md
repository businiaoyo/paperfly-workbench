# 不遮挡内容的窗口操作：0.17.0-test.7

2026-11-13，versionCode **45**，schema **8** 不变。设备为联想 Y700 TB323FU（`HA2HEFTM`，Android 16）。没有发布 NAS，未操作荣耀或 vivo。

## 用户反馈与方案

用户指出 test.6 的常驻“×”难看，并影响应用内容使用。这是交互方案的问题，不能用当时测试通过代替用户认可。本轮删除整套覆盖控件，关闭操作改为按需呈现：

- 轻点已有分隔条，弹出相邻两个应用的图标、名称、方位和文字“关闭”。三应用的第一条管理第一/第二个，第二条管理第二/第三个。
- 拖动仍实时调整比例；超过移动阈值不会弹菜单，取消拖动恢复原比例。
- 菜单不选择或切换应用焦点，关闭动作绑定对应 AppWindow。返回或点外部取消，不更改名单、焦点和比例。
- 菜单末尾保留“调整分屏布局”；单窗口及其他卡片可长按/右键 Dock 图标进入既有“关闭此窗口”。
- 常态不增加标题栏、不缩小内容、不在应用内覆盖关闭按钮。自由窗口继续用已有 WindowChrome；总览继续保持移除。

采用两次明确点击完成关闭，代价是比常驻按钮多一步，收益是使用内容时不遮挡、不误触关闭。菜单只在主动管理窗口时临时出现。

## 模块边界

删除 `WindowCloseButton`、`StageLayout.windowClose`、对应 Activity 创建/定位/清理分支及仅服务旧几何的测试。`SplitDivider.Actions.edit` 传递卡片、相邻边界、方向和锚点；Activity 根据窗口身份绑定动作；`SplitWindowMenu` 独立负责呈现两行成员和布局入口，沿用 WorkbenchDialog / HostModalSurface。分隔条原触摸区、实时预览和提交规则不变。

配置模型和 shell 服务未改，schema 8 不变。关闭继续走现有单窗口后台交还：其余窗口身份、顺序和相对权重保持；关闭非焦点成员保留焦点，最后成员关闭才移除卡片并接续侧栏。test.6 增加的多实例身份、焦点回退及保存快照隔离单元测试保留。

## 实机验证

更新 `WindowCloseValidation`，仍为私有一次性 debug 入口，release 为空实现。本轮使用现场五个应用，没有安装测试应用、接受第三方协议或操作账号。

横屏、竖屏各 **105 项断言通过**：

- 普通、工作台全屏、单应用全屏和主次切换后，应用右上区域没有新增可点击覆盖控件。
- 两条分隔条拖动时实际成员 View 在松手前变化，逻辑画布、显示器和 Surface 保留，不误开菜单；取消恢复草稿。
- 普通/工作台全屏中，两条分隔条的轻点菜单分别只包含对应两个成员；打开与返回取消均保留焦点、草稿、画布、显示器和 Surface。
- 关闭中间成员、当前焦点成员、最后一个成员分别通过菜单实际触摸分发完成；每次只减少目标窗口、释放其显示器，存活成员 Surface/显示器不变，侧栏画布不变。最后一个通过 Dock 上下文菜单关闭。
- 两种全屏、主次交换及还原、侧栏末尾加号打开/关闭选择器保持原资源。
- 测试后通过 App 草稿/添加路径恢复本轮现场，横竖结果的配置均与安装前一致。

另经 ADB 实际输入验证：横屏轻点第二条分隔条显示浏览器/微信及左右方位；竖屏同条显示上下方位。截图和 UI 树确认文字、图标、操作均可见。点击“调整分屏布局”能到原面板；长按 Dock 浏览器图标并松手能打开含“关闭此窗口”的菜单。取消菜单后正常退出首页，再停止本 App 进程重入，配置保持。

这些验证针对 Y700 当前应用及方向，不能据此宣称全部厂商/应用适配完成；测试通过也不代表用户已认可新设计。应用因实际画布变化自行重排的行为不属于本轮新入口的额外 resize。
