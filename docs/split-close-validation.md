## 交互与实现

三应用分屏原来只能从菜单或应用列表移除成员，主画面缺少可发现的独立入口。现在平铺主卡片的每个成员右上角都有“×”，单成员主卡片也保留，便于连续关闭。关闭只作用于该按钮绑定的 AppWindow，不先选择焦点，不删除整组。剩余成员保留顺序、稳定 ID 和相对权重并补满；关闭焦点成员选择存活成员，最后一个成员关闭才删除卡片并接续侧栏。

`WindowCloseButton` 独立负责紧凑的半透明圆底、矢量图标、应用名称提示和点击回调。视觉圆底 32 dp，点击区 48 dp；`StageLayout.windowClose` 将点击区限制在实际显示范围内，支持窄分屏。按钮位于 scene，不嵌入缩放的应用画布，没有增加标题栏或预留内容空间。布局动画和实时分屏预览跟随显示边界，调整期间禁止点击；侧栏和单应用全屏隐藏，自由窗口沿用原 WindowChrome。

`StageActivity` 负责绑定目标、位置、元数据刷新，以及成员移除和切换组合时清理按钮。菜单改为“关闭当前窗口”/“关闭此窗口”。复用既有 `remove`、CardSession、WorkspaceDraft 和服务显示器归属/后台交还路径，没有新增持久字段、shell 权限或第三方依赖。关闭是移出工作台并交还后台，不强行停止应用。

## 实机验证

`WindowCloseValidation` 是仅 debug 可用的有限流程，由私有文件触发，release 为空实现，没有导出测试入口。使用本轮五个现场应用，不安装测试 App、不接受第三方协议、不操作账号。通过 Activity 的真实触摸分发点击关闭控件，等待 Android 异步点击回调后检查结果。

横屏、竖屏各 **114 项断言通过**：

- 普通/工作台全屏每个主成员按钮可见、可点、名称正确且留在所属窗口内；侧栏隐藏。单应用全屏隐藏这些按钮。
- 两种全屏、主次交换及恢复、侧栏末尾加号打开/关闭选择器均保留显示器、Surface 和逻辑画布。
- 关闭中间浏览器仅减少该成员，微信焦点保持，哔哩哔哩与微信的相对比例不变；随后关闭微信，哔哩哔哩占满；再关闭哔哩哔哩，番茄免费小说侧卡片接续主位。
- 每次关闭后确认该显示器已释放，所有存活成员保留原显示器和 Surface，侧栏应用画布不变，旧关闭按钮已从 View 树移除。
- 结束后通过 App 内草稿/添加路径恢复本轮原配置；横竖屏截图确认各按钮位置，无阴影扩散。退出到管理首页、仅停止本 App 进程并重入后配置仍相同。

第一次脚本在 ACTION_UP 同步返回后立即断言，但 ImageButton 将点击回调排到下一次主线程执行，因此误报。实际中间窗口已关闭。修正脚本等待时机，并从本轮安装前快照经 debug 恢复入口/WorkspaceDraft 恢复后重跑，两方向全部通过。恢复文件仅用于本轮流程，不直接覆盖配置文件，验证完成后删除。

这批实机结果针对当前五个应用和 Y700；同组件多实例精确关闭由模型测试覆盖，未在实机新建额外实例。组内画布实际变大/变小时，应用仍可能自行调整页面；没有宣称所有应用或厂商均不会重建。
